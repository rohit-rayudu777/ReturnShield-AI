# Feature Engineering — ReturnShield AI

This document describes the complete feature engineering pipeline used in ReturnShield AI. It covers raw input features, engineered features, encoding strategies, numerical transformations, target definition, leakage prevention, and how the pipeline is reused during inference.

---

## 1. Target Definition

| Column | Type | Description |
|---|---|---|
| `is_abusive_return` | `int` (0 or 1) | **1** = return is classified as abusive (wardrobing, empty box, friendly fraud, etc.). **0** = legitimate return. |

The target is separated from the feature matrix **before any transformation** is applied to prevent any form of target leakage.

---

## 2. Raw Input Features

These are the columns available directly in `data/returns.csv` (generated by `src/data/generator.py`):

### Identifiers (excluded from ML features)

| Column | Type | Description |
|---|---|---|
| `order_id` | `str` | Unique identifier per return event |
| `customer_id` | `str` | Unique customer identifier |
| `timestamp` | `str` | Datetime of the order (used for chronological splitting only) |

### Numerical Features (raw)

| Column | Type | Description |
|---|---|---|
| `order_amount` | `float` | Order value in INR |
| `customer_age_days` | `int` | Age of customer account at time of order |
| `previous_orders` | `int` | Total orders placed by customer before this one |
| `previous_returns` | `int` | Total returns made by customer before this one |
| `customer_return_rate` | `float` | Historical return rate = `previous_returns / previous_orders` (0.0 if no prior orders) |
| `orders_last_7_days` | `int` | Number of orders by this customer in the prior 7 days |
| `orders_last_30_days` | `int` | Number of orders by this customer in the prior 30 days |
| `returns_last_7_days` | `int` | Number of returns by this customer in the prior 7 days |
| `returns_last_30_days` | `int` | Number of returns by this customer in the prior 30 days |
| `average_order_value` | `float` | Historical average order value for this customer |
| `discount_percentage` | `float` | Discount applied to this order (0–70%) |
| `delivery_days` | `int` | Days taken to deliver the order |
| `return_days_after_delivery` | `int` | Days after delivery until return was initiated |
| `address_change_count` | `int` | Number of address changes made by the customer in the past |
| `payment_failures` | `int` | Number of payment failures on this customer's account |
| `previous_chargebacks` | `int` | Number of historical chargebacks filed by this customer |
| `is_first_order` | `int` (0/1) | 1 if this is the customer's first ever order |
| `is_high_value_order` | `int` (0/1) | 1 if `order_amount > 150.0` |

### Categorical Features (raw)

| Column | Values | Description |
|---|---|---|
| `product_category` | `Electronics`, `Clothing`, `Beauty`, `Home`, `Books` | Product category of the returned item |
| `payment_method` | `Credit Card`, `Debit Card`, `UPI`, `Netbanking`, `COD` | Payment method used |
| `item_condition` | `New`, `Damaged`, `Wrong Item`, `Used` | Condition of item at return (if collected) |
| `return_reason` | `Size issues`, `Defective`, `Not as described`, `Late delivery`, `Change of mind` | Customer-stated return reason (if collected) |

> **Note**: `item_condition` and `return_reason` are defined in the pipeline but may not be present in the Phase 2A dataset — the encoder uses `handle_unknown='ignore'` and the pipeline skips columns that are absent from the input DataFrame.

## 3. Engineered Features

All engineered features are computed **deterministically from existing raw columns only**, with no reference to `is_abusive_return`.

| Feature Name | Formula | Risk Intuition |
|---|---|---|
| `previous_return_frequency` | `previous_returns / (previous_orders + 1)` | High historical return rate = elevated risk |
| `return_to_delivery_days_ratio` | `return_days_after_delivery / (delivery_days + 1e-5)` | Very quick returns after long deliveries can indicate abuse |
| `total_return_delay_days` | `delivery_days + return_days_after_delivery` | Total time from order to return initiation |
| `refund_to_order_value_ratio` | `order_amount / (average_order_value + 1e-5)` | This order being significantly above avg value = elevated risk |
| `returns_velocity_ratio_7d_30d` | `returns_last_7_days / (returns_last_30_days + 1)` | Spike in short-term return activity vs. monthly baseline |
| `recent_returns_to_orders_ratio_7d` | `returns_last_7_days / (orders_last_7_days + 1)` | Fraction of recent orders being returned (7d window) |
| `recent_returns_to_orders_ratio_30d` | `returns_last_30_days / (orders_last_30_days + 1)` | Fraction of recent orders being returned (30d window) |
| `payment_failure_rate` | `payment_failures / (previous_orders + 1)` | History of payment failures signals risky behaviour |
| `address_change_rate` | `address_change_count / (previous_orders + 1)` | Frequent address changes can indicate fraudulent activity |
| `chargeback_rate` | `previous_chargebacks / (previous_orders + 1)` | Chargebacks strongly correlate with abuse |
| `orders_velocity_ratio_7d_30d` | `orders_last_7_days / (orders_last_30_days + 1)` | Detects unusual ordering bursts in short windows |
| `order_frequency_days` | `customer_age_days / (previous_orders + 1)` | Average days between orders; low = high-frequency buyer |
| `high_value_return_interaction` | `is_high_value_order * customer_return_rate` | Interaction: high-value order × already-high return rate |

## 4. Numerical Transformations

All numerical features undergo the following processing during `FeatureEngineer.transform()`:

1. **Missing value imputation**: Missing values are filled with the **median** computed on the training set during `fit()`. Median is preferred over mean for robustness to outliers.
2. **Clipping**: All raw numerical columns are clipped to `>= 0.0` to prevent logically invalid negative values (e.g., negative order counts).
3. **Infinite value replacement**: Any `inf` or `-inf` values arising from engineered feature calculations (e.g., division by near-zero) are replaced with `0.0`.
4. **NaN cleanup**: Any residual `NaN` in engineered columns is filled with `0.0` after the above steps.

No log transforms or standardisation are applied at this stage — those are delegated to the model training pipeline, which may apply scaling as needed.

## 5. Categorical Encoding Strategy

Categorical features are encoded using **OneHotEncoder** from `scikit-learn` with the following configuration:

```python
OneHotEncoder(
    categories=[predefined_list],  # fixed category list
    handle_unknown='ignore',        # unseen values produce all-zero row
    sparse_output=False             # returns dense numpy array
)
```

**Why predefined categories?**

- The encoder is fitted on the **training set only** (inside `FeatureEngineer.fit()`).
- During inference on new data, previously unseen category values (e.g., a new payment method) will produce an **all-zero row** rather than raising an error, thanks to `handle_unknown='ignore'`.
- The fixed, predefined category lists also ensure the **feature column count and order** are identical at training time and inference time.

**Predefined categories:**

| Column | Categories |
|---|---|
| `product_category` | `Electronics`, `Clothing`, `Beauty`, `Home`, `Books` |
| `payment_method` | `Credit Card`, `Debit Card`, `UPI`, `Netbanking`, `COD` |
| `item_condition` | `New`, `Damaged`, `Wrong Item`, `Used` |
| `return_reason` | `Size issues`, `Defective`, `Not as described`, `Late delivery`, `Change of mind` |

## 6. Target Leakage Prevention

The following design decisions prevent target leakage:

1. **Target separation first**: `load_and_preprocess_data()` extracts `is_abusive_return` into `y` before any feature processing begins. The column is never passed to `FeatureEngineer`.
2. **No derived features from target**: All engineered features use only raw behavioral columns available at the time the return is initiated.
3. **Chronological splitting by default**: `prepare_data_splits()` uses chronological ordering so the model never trains on future data. This prevents temporal leakage.
4. **Fit on train only**: `FeatureEngineer.fit()` is called only on the training split. Medians and encoder categories are computed from training data alone, then applied to the test split via `transform()`.
5. **No post-classification information**: Features such as "was the return approved?" or "was refund issued?" are never included — these are only known after the return is reviewed.

---

## 7. Train / Validation / Test Split Logic

The `prepare_data_splits()` function in `feature_engineering.py` supports two split strategies:

### Chronological Split (default, recommended)
```python
train_df, test_df = prepare_data_splits(df, test_size=0.2, split_method="chronological")
```
- Sorts the dataset by `timestamp`.
- Uses the **first 80%** (oldest records) as training data and **last 20%** (most recent records) as test data.
- **Recommended** for transaction/time-series data to simulate real-world deployment conditions.

### Random Split (for comparison / ablation)
```python
train_df, test_df = prepare_data_splits(df, test_size=0.2, split_method="random", random_state=42)
```
- Uses `train_test_split` with stratification on the target.
- Fixed `random_state` ensures reproducibility.
- Not recommended as the primary split strategy due to temporal leakage risk.

## 8. Pipeline Usage — Training vs. Inference

### During Model Training

```python
import pandas as pd
from src.features.feature_engineering import (
    FeatureEngineer, load_and_preprocess_data, prepare_data_splits
)

# 1. Load data and separate target
df_raw, y = load_and_preprocess_data("data/returns.csv")

# 2. Split chronologically
train_df, test_df = prepare_data_splits(df_raw, test_size=0.2, split_method="chronological")
y_train = train_df["is_abusive_return"]
y_test  = test_df["is_abusive_return"]

# 3. Fit on training data only — compute medians and encoder categories
fe = FeatureEngineer()
X_train = fe.fit_transform(train_df)   # fit + transform training data
X_test  = fe.transform(test_df)        # transform test data using training statistics

# 4. Train model (Phase 2C)
# model.fit(X_train, y_train)
```

### During Online Inference

```python
import pandas as pd
import pickle
from src.features.feature_engineering import FeatureEngineer

# Load pre-fitted FeatureEngineer (saved after training)
with open("models/feature_engineer.pkl", "rb") as f:
    fe = pickle.load(f)

# Single return request as a DataFrame row
request = pd.DataFrame([{
    "order_id": "ORD_123456_0",
    "customer_id": "CUST_000001",
    "order_amount": 249.99,
    "product_category": "Electronics",
    "payment_method": "COD",
    "customer_age_days": 45,
    "previous_orders": 2,
    "previous_returns": 2,
    "customer_return_rate": 1.0,
    # ... all required fields
}])

# Transform using training-fitted parameters
X_inference = fe.transform(request)

# Score with model (Phase 2C)
# risk_score = model.predict_proba(X_inference)[0, 1]
```

> **Key principle**: The `FeatureEngineer` object is fitted **once** on training data and **saved**. At inference time it is loaded and only `transform()` is called — never `fit()` again. This ensures consistent preprocessing across training and production.
